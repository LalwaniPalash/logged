# Logged iOS Widget

**Status: wired and building** (2026-07-26). The `LoggedWidgetExtension` target exists in
`ios/Runner.xcodeproj`, the App Group is active on both targets, and
`flutter build ios --simulator --debug` embeds `LoggedWidgetExtension.appex` at
`MinimumOSVersion 14`.

This file records how it was set up, because none of it is reproduced by the Flutter
tool — if `ios/` is ever regenerated, every step here has to be redone by hand.

## Contents

- `LoggedWidget.swift` — the widget, its timeline provider, and the entry view. Reads
  its values from the shared app-group `UserDefaults`.
- `LoggedWidgetBundle.swift` — the `@main` bundle. Deliberately lists only
  `LoggedWidget()`.
- `Assets.xcassets`, `Info.plist` — generated by the Xcode template; the extension
  target needs them.

## How it was wired (redo this if ios/ is regenerated)

1. Open `ios/Runner.xcworkspace` (not the `.xcodeproj`).
2. `File > New > Target… > Widget Extension`. Xcode names the target
   `LoggedWidgetExtension`; that is fine and does not need renaming — the Dart side
   matches on the widget's `kind` string, not the target name.
3. Delete the template files Xcode adds beyond the two listed above —
   `AppIntent.swift`, `LoggedWidgetControl.swift`, `LoggedWidgetLiveActivity.swift` —
   and trim `LoggedWidgetBundle.swift` to list only `LoggedWidget()`. The Control and
   Live Activity templates need much newer iOS APIs than this widget does.
4. **Set the extension's Minimum Deployment to iOS 14.0.** Xcode defaults a new
   extension to the newest SDK it ships with (26.4 at the time of writing), which
   would silently never install on a real phone.
5. Add the **App Groups** capability with `group.com.palash.logged` to **both**
   `Runner` and `LoggedWidgetExtension`.
6. **Move "Embed Foundation Extensions" before "Thin Binary"** in
   `Runner > Build Phases`. See the build-cycle note below.
7. `Runner > Signing & Capabilities > + Capability > HealthKit`, for the Health
   export. Xcode picks up the existing `Runner/Runner.entitlements`.

## Two traps worth remembering

**The Xcode template overwrites this widget's source.** The Widget Extension template
generates a file called `LoggedWidget.swift` — the same name as the hand-written one
here — and silently replaced it (5114 → 2596 bytes, dropping the app-group read). If
the widget suddenly renders template placeholder text, check this file against git
before debugging anything else.

**`Cycle inside Runner` on build.** Xcode appends "Embed Foundation Extensions" as the
*last* build phase, after Flutter's "Thin Binary" script. Thin Binary declares no
outputs, so Xcode assumes it may touch anything inside `Runner.app` — including
`PlugIns/` — which makes the appex copy both depend on and appear to invalidate it.
Moving Embed Foundation Extensions ahead of Thin Binary breaks the loop.

## Invariants the Dart side depends on

| Thing | Value | Also defined in |
| --- | --- | --- |
| App Group | `group.com.palash.logged` | `LoggedWidgetKeys.appGroupId`, `HomeWidgetService._iosAppGroupId`, both targets' entitlements |
| Widget `kind` | `LoggedWidget` | `HomeWidgetService._iosWidgetName` |

If the App Group does not match everywhere, the app writes to its own sandbox and the
widget shows its placeholder text forever — with no error on either side.

The widget has never been placed on a real home screen. It is build-verified only.
