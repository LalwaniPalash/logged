# Full-app audit — 2026-08-14

Scope: all logic (set/rep logging, rank, weekly volume, rest timer, deload, streak), Flutter
practice, user flow, CRUD + confirmation coverage. **No code changed.**

Baseline: `flutter analyze` clean, `flutter test` 230/230 green. Every finding below survives both —
consistent with `tasks/lessons.md` ("green tests are necessary, not sufficient").

---

## A. Correctness — data & math

### A1. Warm-up sets count toward weekly volume and PRs 🔴
`lib/data/repositories/analytics_repository.dart` `_query` (~line 97) has **no `is_warmup = 0`
filter**, unlike `_benchmarkQuery`, `_deloadQuery`, and the muscle-progress path (which skip warmups
explicitly). `_query` feeds `completedSetsProvider` → `weeklyStats`, `muscleVolumeThisWeek`,
`recentPrs` (`progress_screen.dart:80-81`, `active_session_screen.dart:534`).

Effect: the "Weekly volume" chart is inflated by every warm-up rung — typically 20–30% on a
barbell-heavy program, and more for anyone using the auto-warmup generator.

### A2. Bodyweight-only sessions are invisible to weekly volume and session counts 🔴
Same `_query`: `AND se.weight_value IS NOT NULL`. A pull-up / push-up / dip session contributes
**0 volume and 0 to `WeekStat.sessions`**. The chart reads "you didn't train" for a real workout.

This is the same class of bug already fixed once for strength standards — `_benchmarkQuery`'s own
comment says the weighted-sets query "hid the Pull-Up benchmark for anyone training it unweighted."
The fix was applied to standards only; weekly stats and PRs still have it.

### A3. `SetRepository.edit` resets unpassed fields to defaults 🟠 (latent, high blast radius)
`lib/data/repositories/set_repository.dart:60-77`:
```dart
weightEntry: Value(weightEntry ?? WeightEntry.total),
sideCount:   Value(sideCount ?? 1),
loadingMode: Value(loadingMode ?? LoadingMode.external),
isWarmup:    Value(isWarmup ?? false),
```
A null argument means "not supplied", but the code writes the **default** rather than leaving the
column alone. Both current callers happen to pass every field, so it is latent today — but this is
exactly the bug `lessons.md` already records once ("delete-resets-logging-defaults"). Any future
partial edit silently converts a per-hand assisted set into a total-load external working set.

Correct shape: `Value.absent()` when the arg is null. `rpe`, `notes`, `distanceMeters`, `durationSec`
have the same issue and additionally cannot currently be *cleared* vs *left alone* — the API can't
express the difference.

### A4. `sideCount` multiplies a 1RM proxy 🟠
`lib/core/domain/muscle_progress.dart` `_performanceSignal`:
```dart
value: load * sides * (1 + record.reps! / 30)
```
`load` is already `totalLoadKg(...)`, which doubles for `WeightEntry.perSide`. Then `sides`
(the each-side rep multiplier) multiplies it again.

5 reps each leg at 20 kg is not a 40 kg lift. Ground rule 5 of the T1–T3 spec says est-1RM uses the
entered value, and `WorkoutSetRecord.estimatedOneRepMaxKg` obeys it — this one doesn't. Two screens
therefore report different "strength" for the same set.

Real-world impact: because the index is relative to a per-exercise baseline, a user who toggles
"Each side" or "Per hand" partway through their history sees the index jump ~2×, clamp at 175, and
rank-up instantly. Confirms the open item in memory ("sideCount not counted in muscle-set
landmarks") — but the inconsistency runs the other way too: `sideCount` is ignored in
`primarySets`/`effectiveSetHistory` while being counted in the strength signal.

### A5. Streak silently depends on a setting most users never open 🟠
`WorkoutSettings.defaults` = `restWeekdays: {7}` (Sunday only). `computeStreak` only bridges a gap
on a day that is trained **or** a rest day. A Mon/Wed/Fri lifter who never opens Settings has a
streak permanently stuck at 1, and `_weekStates` (`dashboard_screen.dart`) marks Tue/Thu as
`WeekDayState.missed` — the dashboard tells a perfectly consistent user they failed twice a week.

Onboarding does not ask for training days. Either infer rest weekdays from logged history, or make
the streak tolerant of N non-training days per week.

### A6. `SessionRepository.addExercise` can create duplicate positions 🟠
```dart
position: rows.length
```
3 exercises at positions 0,1,2 → remove the middle → 0,2 remain → add → `rows.length == 2` → two
rows at position 2. Ordering becomes non-deterministic, and `reorderExercises` inherits the
ambiguity. `template_repository.dart:96` does it correctly (`max(position) + 1`); the session path
doesn't. Mid-workout exercise removal is a common flow, so this is reachable.

### A7. `SessionRepository.finish(id)` wipes session notes 🟡
`notes: Value(notes)` with `notes` defaulting to null → writes SQL NULL over any existing note.

### A8. Deload detector has no recency window and is near-permanently "on" 🟠
`_deloadQuery` has **no date filter** — it loads the entire set history on every evaluation
(performance), and:
- `stalledLifts` flags any lift whose est-1RM hasn't risen >1% across its last **3 recorded days** —
  which may span six months for an accessory. Every maintenance lift qualifies.
- `rpeAtLoadSeries` picks the most-populated load bucket across all time, then reads its last 3
  values — again with no recency bound.

Since `triggered: reasons.length >= 2` and the stall reason is essentially always present, a single
additional signal flips the deload card on. Expect false deload prompts.

### A9. PRs compare across `weightEntry` 🟡
`recentPrs` ranks on `estimatedOneRepMaxKg`, which uses the **entered** value. Log a DB press as
`30 per hand`, later re-log as `60 total` → a fake all-time PR and a celebration dialog.

### A10. `_volumeAdequacy` has step discontinuities 🟡
`muscle_progress.dart`: 7.9 effective sets → 0.55, 8.0 → 0.75. At MRV → 0.75, MRV + 0.1 → 0.55.
A fractional set moves the rank score by a visible chunk in both directions. Intentional as a
threshold model, but users will read it as the app being erratic.

### A11. `muscleVolumeThisWeek` uses the legacy `muscle_group` string 🟡
Everything else in the app is on the 27-id `MuscleId` taxonomy. Two parallel muscle vocabularies.

## B. Flutter best practice

### B1. Streams and Futures constructed inside `build()` 🟠
- `dashboard_screen.dart:64` → `StreamBuilder` at :205
- `history_screen.dart:28` (`watchRecent(limit: 500)`)
- `templates_screen.dart:173`
- `progress_screen.dart:191` (`_loadExercise(...)` future)
- `active_session_screen.dart:668` uses a cached `_future` — correct, and shows the right pattern

Each rebuild creates a **new** subscription. `snapshot.data ?? const []` then renders the *empty
state* while the new stream reconnects, so the recent-sessions list, history list, and template list
visibly flash empty on unrelated rebuilds (theme change, keyboard, a rank update firing
`_handleRankUpdates`). Riverpod `StreamProvider` is already used elsewhere in this codebase.

Related: none of these distinguish **loading** from **empty** — first paint shows "no templates yet".

### B2. N+1 queries in `SessionRepository.details()` 🟡
One `select` per exercise plus one per set list, in a loop. A 10-exercise session = 21 round trips,
re-run on every `setState(_refresh)`.

### B3. `DateTime.now()` read inside `build()` 🟡
`dashboard_screen.dart:70`. The greeting, week strip, streak, and "missed" markers do not update
when the app is left open across midnight.

### B4. `_syncBackgroundNotification` fires on `AppLifecycleState.inactive` 🟡
On iOS that includes every notification-centre pull and app-switcher peek — schedule/cancel churn
against the native plugin for a transient state.

## C. Rest timer

### C1. Android notification is scheduled INEXACT 🟠
`notification_service.dart:162` — `AndroidScheduleMode.inexactAllowWhileIdle`. Android may delay an
inexact alarm by minutes. For a 90-second rest timer, the notification is the entire feature; delayed
by even 60s it is worse than useless. The trade-off (avoiding the `SCHEDULE_EXACT_ALARM` permission)
is defensible but should be deliberate and documented — right now it silently degrades the headline
behaviour.

### C2. No visual completion state 🟡
`_finish()` sets `running: false`; `RestTimerBar` returns `SizedBox.shrink()` when `!running`. The
bar simply disappears with a haptic. If the phone was in a pocket, there is nothing on screen saying
rest finished or how long ago.

### C3. Timer is app-scoped but keyed to one session 🟢
`cancel(sessionId:)` on dispose and the `state.sessionId != sessionId` guard in the bar are correct.
`endTime` (not tick count) being authoritative on resume is the right design. No issue.

## D. CRUD completeness & confirmation coverage

Present and correct: template delete (confirms), workout delete (confirms), exercise swap
(confirms — it destroys sets), backup import (confirms, "cannot be undone").

### D1. Removing an exercise from a session — NO confirmation 🔴
`active_session_screen.dart:187` `_removeExercise` → `removeSessionExercise` deletes the exercise
**and every set logged under it**, immediately, from a tap at :754. "Replace exercise?" confirms for
the same destruction; this path doesn't.

### D2. Deleting a set — NO confirmation 🟠
`set_editor_sheet.dart` header trash icon → pops straight through to `setRepository.delete`.

### D3. Deleting a bodyweight entry — NO confirmation 🟠
`settings_screen.dart:1588` — `onPressed: () => repo.delete(entries[i].id)`. This retroactively
changes every bodyweight, added-weight, and assisted calculation in history (they resolve via
`_bodyweightOnOrBefore`). Highest-consequence unconfirmed delete in the app.

### D4. Exercises: no DELETE, no RENAME 🟠
`ExerciseRepository` exposes `add`, `archive`, and field-specific updates only. A custom exercise
created with a typo can never be renamed or removed — only hidden. The name is also the UNIQUE key,
so the typo blocks recreating it correctly.

### D5. Sessions: no EDIT 🟠
No UI to change a session's date/time or notes. `start({startedAt})` and `finish({endedAt, notes})`
already accept them. Consequence: **you cannot log yesterday's workout.** Forget to open the app and
that session is either lost or stamped with the wrong date, which then corrupts streak, weekly
volume bucketing, and rank recency.

### D6. No undo, anywhere except the rest-day toggle 🟡
The only `SnackBarAction` in the app is at `settings_screen.dart:1683`. Delete-then-undo-snackbar
would cover D1/D2/D3 with less friction than three modals — modals on every set delete would be
punishing during a workout. Recommendation: **modal for D1 and D4/D5-scale destruction, snackbar-undo
for D2 and D3.**

## E. User flow observations

1. **Two overlapping "×2" controls in one sheet.** `Per hand (×2)` multiplies the weight; `Each side
   (×2)` multiplies the reps. The echo lines do a genuinely good job explaining each in isolation,
   but there is no combined echo for the case where both are on — and that case is where the volume
   math quadruples. One line stating total volume for the set would remove all ambiguity.
2. **`sideCount` is hard-limited to 1 or 2** (bool toggle in both the set editor and template
   editor) while the column is an `int`. Consistent, so no data loss — but tri-set / three-position
   work can't be expressed.
3. **Set completion is inferred, never confirmed.** `isSetComplete` decides when to start the rest
   timer from field contents. Typing "1" of "12" reps momentarily makes the set complete and starts
   the rest timer. Worth checking against a debounce.
4. **First paint of the dashboard shows Foundation / 0%** while providers resolve, because every
   `.asData?.value ?? default` falls back to a zero state rather than a skeleton. New users see a
   ranked-zero screen before their real data appears.
5. **Deload card and rank-up snackbar can both fire on the same emission** — the rank listener writes
   to `app_settings`, which is watched, which recomputes. The `mapEquals` guard breaks the infinite
   loop (documented in the code), but the coupling remains fragile.

# Round 2 — creation flows & "column exists, no writer"

Triggered by a real user report: **Copenhagen planks had to be logged as 30 reps/side instead of
30 seconds/side.** Round 1 audited logic and CRUD on existing records; it did not trace the
*creation* flows. This section does.

## F1. A custom exercise cannot be marked as timed 🔴 — the Copenhagen plank bug

**Root cause: `Exercises` has no `isTimed` / `defaultDurationSec` column.** Timed-ness is *inferred*
at render time (`set_row.dart:isTimedExercise`):

```dart
if (sets.isNotEmpty) {
  return sets.any((s) => s.durationSec != null) && sets.every((s) => s.reps == null);
}
return targetDurationSec != null && minReps == null && maxReps == null;
```

For a brand-new custom `bodyweight`/`strength` exercise logged ad hoc: `sets` is empty, and
`targetDurationSec` is null (no template) → `timed == false`. The set editor then reads:

```dart
bool get _showsDuration =>
    category == cardio || category == stretching ||
    widget.timed ||                       // false
    widget.existing?.durationSec != null || // false
    widget.seed?.durationSec != null;       // false
```

→ **the duration field is never rendered**, and `_showsReps => _isLifting` is true. Reps are the only
option.

**It is a chicken-and-egg.** The only two unlocks are (a) a set that already has `durationSec`, or
(b) a `targetDurationSec` prescription — and the prescription is editable **only in the template
editor** (see F7). There is no path from the "Custom exercise" sheet to a timed set.

**Every escape hatch is a trap:**

| Workaround | What it costs |
|---|---|
| Category `stretching` | `_showsWeight => _isLifting` excludes stretching → **a weighted plank can never be logged**. Also misfiles the exercise in the picker and changes rank semantics. |
| Category `cardio` | `isSetComplete` for cardio requires duration **AND** distance > 0 → the set never reads complete → **the rest timer never auto-starts**. |
| Build a one-exercise template just to set `targetDurationSec` | Works, and is completely undiscoverable. |

**Affected movements:** Copenhagen plank, side plank, dead hang, L-sit, wall sit, hollow hold,
Nordic hold, ab wheel hold, any isometric — i.e. a whole training modality.

**The right fix is a column, not a UI patch.** Add `Exercises.isTimed` (or
`defaultDurationSec`), expose it as a "Logged in seconds" toggle in the custom-exercise sheet, and
have `isTimedExercise` prefer it. Per `lessons.md` ground rule 2 that means a migration **and** a
one-time backfill (existing `stretching`/timed library rows). Inferring a fundamental property of an
exercise from its own history can never work for the first entry.

## F2. Distance has the identical chicken-and-egg 🟠
```dart
bool get _showsDistance => category == cardio || widget.existing?.distanceMeters != null;
```
A farmer's carry, sled push, sandbag carry, or yoke walk filed as `strength` can **never** record
distance. Same shape as F1, same fix.

## F3. Exercise name, category, and bodyweight factor are write-once 🟠
`ExerciseRepository` exposes `add`, `archive`, `updateMuscles`, `updateVideoUrl`,
`updateDefaultUnit`, `updateLoggingDefaults`. There is **no** `updateName`, `updateCategory`, or
`updateBodyweightFactor`. Settings' exercise editor (`settings_screen.dart:426`) edits muscles only.

`bodyweightFactor` is the dangerous one: it scales every bodyweight / added / assisted resisted-mass
calculation (`muscle_progress.dart:_resistedMassKg`) and therefore every rank and strength-standard
number for that lift. Type `0.6` when you meant `0.06` and it is permanent — and because there is no
delete (D4) and `name` is UNIQUE, you cannot even recreate the exercise correctly. Archive-and-rename
is impossible; archive alone leaves the bad data in every historical calculation.

Combined with F1: **you cannot fix a wrong category either**, so a Copenhagen plank filed as
`stretching` to unlock seconds is stuck there forever.

## F4. Every custom exercise is hardcoded to `muscleGroup: 'custom'` 🟡
`settings_screen.dart:384`. `muscleVolumeThisWeek` groups by `muscleGroup`, so all custom exercises —
regardless of what they train — merge into one "custom" row. (This is also the legacy taxonomy flagged
in A11; custom exercises make it strictly worse.)

## F5. `Sessions.notes` has no writer anywhere 🟠
`active_session_screen.dart:531` calls `finish(widget.sessionId)` with no notes, and nothing else
writes the column. **You cannot write a note about a workout** — "felt awful, slept 4h", "gym was
packed, cut it short" — which is exactly the context that explains a bad session six weeks later.
The column, the repo parameter, and the backup serialisation all exist. Only the UI is missing.

(Note this compounds A7: `finish` writing `Value(null)` means that even if a note were set earlier,
finishing the workout erases it.)

## F6. `RestDays.note` has no writer 🟢
`RestDayRepository.log(date, {note})` — both call sites (`settings_screen.dart:1631`, `:1687`) omit
it. Dead field. Low stakes, but it is unused surface area.

## F7. The prescription is read-only inside a session 🟠
`_formatPrescription` (`active_session_screen.dart:1195`) **renders** targetSets, min/maxReps,
targetDurationSec, targetDistanceMeters, restSeconds, tempo — and nothing in the session screen
edits any of them. They are writable only in the template editor.

Two consequences, both large:

1. **The progression coach never engages for ad-hoc users.** `suggestNextSet` returns
   `'Match last time; add a rep range and target RPE to progress.'` whenever `minReps`, `maxReps`, or
   `targetRpe` is null. `targetRpe` is parsed out of `prescriptionNotes` (`_targetRpe`), which is
   also template-only. Start a workout without a template and the entire T2 coaching layer is
   silently inert — with a message telling you to add fields you have no way to add.
2. **It is the only unlock for F1/F2**, and it lives on a different screen from the problem.

## F8. `weightEntry` is not exposed at exercise creation 🟡
`ExercisesCompanion.insert` in the custom sheet omits it → defaults to `total`. For a dumbbell
exercise the user must discover the per-hand toggle inside the set editor; it is then learned as a
side effect of `updateLoggingDefaults`. The creation sheet asks for `loadingMode` and
`bodyweightFactor` but not this.

## F9. `defaultUnit: const Value(WeightUnit.kg)` is hardcoded at creation 🟡
Same line. An lb-first user gets every custom exercise in kg until they toggle it per exercise.
There is no global default-unit preference feeding this.

## F10. Category choice has unexplained semantic consequences 🟠
The category chips read as pure taxonomy — "where does this get filed" — but each one silently
rewires the logging form and the completion rule:

| Category | Weight field | Reps | Duration | Distance | `isSetComplete` requires |
|---|---|---|---|---|---|
| strength | ✅ | ✅ | only if timed | only if present | (see `set_row.dart`) |
| bodyweight | ✅ (unless mode=bodyweight) | ✅ | only if timed | only if present | — |
| stretching | ❌ | ❌ | ✅ | ❌ | duration > 0 |
| cardio | ❌ | ❌ | ✅ | ✅ | duration > 0 **AND** distance > 0 |

Nothing in the sheet says any of this. A user picking `cardio` for a timed hold gets a set that can
never be complete, which silently disables the rest timer auto-start — with no error and no hint.

## Pattern behind F1–F10

Round 1 found bugs in code that runs. This round found a consistent architectural choice:
**properties of an exercise are inferred from its history rather than declared on the exercise.**
That is elegant for the seeded 1278-exercise library, where the library file declares everything —
and it collapses for user-created exercises, which have no history and no library row. Every custom
exercise starts in a state the inference cannot resolve, and the app offers no way to declare the
answer.

The general fix is one migration adding the declared properties the creation sheet should ask for
(`isTimed`, and an editable `category` / `bodyweightFactor` / `name`), plus making the prescription
editable in-session so the ad-hoc path is not a second-class citizen.

## Revised fix order

| # | Fix | Why |
|---|---|---|
| 1 | F1 + F2 — `Exercises.isTimed`, exposed at creation, editable later | A whole modality is unloggable; user-reported |
| 2 | F3 — exercise edit (name / category / bodyweightFactor) + delete | Every F1 workaround is permanent without it; bad `bodyweightFactor` silently corrupts rank |
| 3 | F7 — editable prescription in-session | Unlocks the coach for ad-hoc users and removes the F1 chicken-and-egg |
| 4 | A1 + A2 — warm-up and bodyweight filters in `_query` | One-line SQL each; corrects the headline weekly-volume number |
| 5 | D1 — confirm before removing a session exercise | Silent unrecoverable data loss |

F5 (session notes) is a small, high-value add: the column, repo parameter, and backup format already
exist — it needs a text field on the finish dialog and A7 fixed so it isn't nulled.

# Round 3 — muscle bias, set/rep logging, bundled-exercise CRUD

## G. Muscle bias

### G1. The set editor writes SHARE semantics; the domain expects MULTIPLIER semantics 🔴

This is the most consequential finding in the audit.

**Domain side** (`muscle_progress.dart`, `live_muscle_state.dart`), for each primary muscle:
```dart
final weight = primaryMuscleBiasWeight(muscle: muscle, weights: record.muscleBiasWeights) ?? 1.0;
acc.primarySets += weight;
```
The null fallback is **1.0 per muscle**. One set of a 3-primary Zercher squat with no bias credits
quads 1.0 **and** glutes 1.0 **and** hams 1.0 — total 3.0. That is correct hypertrophy convention and
it matches the per-muscle landmarks (quads MEV 8, glutes MEV 8, hams MEV 6 are independent budgets).

**UI side** (`set_editor_sheet.dart:_normalizeBiasWeights`) forces the weights to **sum to 1.0**
across the primaries, and `_biasPercentages` renders them as percentages of one set
("50% Quads · 30% Glutes · 20% Hamstrings").

The two disagree about what the number means. Consequences:

| Exercise | Never opened the sheet | Opened the sheet (even without moving a slider) |
|---|---|---|
| 2 primaries | **2.0** effective sets | **1.0** |
| 3 primaries | **3.0** | **1.0** |

**Opening the set editor halves — or thirds — your credited volume.** `_save()` writes
`_effectiveBiasWeights` whenever `_showsMuscleBias` is true, so merely opening the sheet and hitting
Save applies the even-split default, which is the worst case.

**The sharper framing: using bias can only ever reduce credited volume, never increase it.**
Biasing 100% to quads gives quads 1.0 — exactly the no-bias value. Every other setting is strictly
below it. A user who drags the slider to 70% quads to say "this hits quads harder" gets quads
**0.7** — less than if they had never touched it.

Downstream: `primarySets` → `effectiveSetHistory` → `_rankScore` (volume + consistency = 50 of 100
points) → `MuscleRank`, plus the sculpture's `VolumeZone` and every MEV/MAV/MRV readout.

**Why the tests don't catch it.** `muscle_progress_test.dart` and `live_muscle_state_test.dart` feed
weights straight into the domain and never run the UI's normalizer, so they encode multiplier
semantics. Two currently-green assertions are mutually contradictory as a unit:
- `:58` — 3 sets, no bias → `chest.primarySets == 3` (3.0 **per muscle**)
- `:362` — 3 sets, biased → quads 1.833 + glutes 0.633 + hams 0.533 = 3.0 **total across 3 muscles**

Same three sets, 3× different credit. Both pass. Textbook seam bug — the units are only wrong where
the UI meets the domain, and no test crosses that seam.

**Fix:** normalize so the **mean** is 1.0 (i.e. sum = number of primaries), not the sum. Then
50/50 → 1.0/1.0 (identical to no bias — the correct neutral), 70/30 → 1.4/0.6. Bias then
redistributes emphasis around a fixed total, which is what the UI copy already implies. Keep the
percentage display; only the persisted scale changes. Needs a migration for already-written weights.

### G2. Three different effective-set computations, one set of landmarks 🟠
`analytics_repository.loadDeloadData`:
```dart
for (final muscle in primary) { weekly[muscle]![weekIndex] += 1; }
```
Bias is **ignored entirely** on the deload path.

| Path | Primary credit per set |
|---|---|
| `buildLiveMuscleState` (3D sculpture, weekly balance) | bias-weighted |
| `buildMuscleProgress` (rank, MEV/MAV readouts) | bias-weighted |
| `loadDeloadData` (deload trigger) | **always 1.0** |

All three are compared against the same `VolumeLandmarks`. With G1 in play the deload assessor sees
up to N× what the sculpture sees for the identical week — so it can report "exceeded MRV for two
weeks" while the sculpture shows the muscle mid-band. Compounds A8 (deload already over-fires).

### G3. Secondary muscles cannot be biased 🟡
`secondarySets` is an `int`, incremented by 1 and multiplied by `secondaryMuscleSetWeight` (0.35).
Biasing a press 100% to upper chest still credits front delts full secondary volume. Structurally
unbiasable — the field would have to become a double.

### G4. Bias propagates silently and permanently 🟡
`SetSeed.fromSetEntry` carries `muscleBiasWeights` forward; `_addSet` seeds from it; and
`seedForNextSet` falls back to `lastSetForExercise` across sessions. One trip through the sheet
biases **every subsequent set of that exercise, in every future workout**. With G1 that means one
curious tap permanently halves that exercise's volume contribution.

### G5. Bias is invisible outside the editor 🟡
`set_row.dart:_deviations` flags loading mode, unit, weightEntry, and sideCount deviations — but not
bias. A set carrying 90/10 bias renders identically to a 50/50 one. The comment on `_deviations`
says silence must mean "the heading is accurate for this row"; bias breaks that contract.

## H. Set & rep logging

### H1. Set numbers gap permanently after a delete 🟠
`SetRepository.delete` never renumbers, and `_nextSetNumber` is `max(setNumber) + 1`. Delete set 2 of
3 → the rows read **1, 3**, and the next add is **4** → 1, 3, 4. `shiftSetNumbers` exists and is
wired only into `insertWarmupSets`. Mid-workout this reads as data loss.

### H2. Sets cannot be reordered or inserted mid-list 🟠
`onReorder` (`active_session_screen.dart:723`) reorders **exercises**. There is no set-level reorder
and no "insert set above". The only writers are append (`_addSet`, `_repeatSet`) and the warm-up
prepend. Log a set out of order and the only repair is deleting and re-entering everything after it —
which then also triggers H1.

### H3. A completely empty set can be saved 🟡
`_save()` validates only assisted-load-vs-bodyweight. Every field is `int.tryParse` / `double.tryParse`,
so blank input becomes null and is written. `isSetComplete` then hides it from the rest timer, but the
row persists and enters history as a real set.

### H4. Warm-up sets have no number 🟡

# Round 4 — why the deload feature has never appeared

The user reports never having seen deload work. It is not a rendering bug: **the trigger is
effectively unreachable by construction.** Full chain below.

## The gate

`deload.dart:assessDeload` returns `triggered: reasons.length >= 2` — **two of three** signals must
fire simultaneously.

### Signal 1 — rising RPE at load: structurally dead 🔴
```dart
recent[1] >= recent[0] && recent[2] >= recent[1] && recent.last - recent.first >= rpeRise
```
Requires ≥3 logged RPE values for the same exercise **at the same load** (bucketed by
`loadKg.toStringAsFixed(2)`), monotonically non-decreasing.

**There is no RPE input in the inline set row** — `grep rpe lib/features/session/widgets/set_row.dart`
returns nothing. RPE exists only in the set editor sheet, and is optional there. Any user logging via
the fast inline path (the default) has `rpe == null` on every set, so `rpeAtLoadSeries` is empty and
this signal can never fire.

### Signal 2 — overreaching: near-impossible 🔴
```dart
values.length >= 2 && values[len-2] > mrv && values.last > mrv
```
`loadDeloadData(weeks: 4)` builds `weekStarts` as `[3wk ago, 2wk ago, 1wk ago, current]`, so
**`values.last` is the CURRENT, PARTIAL week** — and it is compared against a full-week MRV.

On Monday the current week holds ~0 sets, so `values.last > mrv` is false. The signal can only fire
very late in a week, and only if the *previous* week also exceeded MRV. Concretely, for quads
(MRV 26) that means 26+ effective sets last week **and** 26+ already banked this week.

Compare against a completed week, or prorate the current week by days elapsed.

### Signal 3 — stalled lifts: fires almost always 🟡
```dart
recent.last <= recent.first * (1 + stallTolerance)   // stallTolerance = 0.01 × sensitivity
```
Any lift whose est-1RM has not risen >1% across its last **3 recorded days** counts — and those days
carry no recency bound (A8), so an accessory trained three times over six months qualifies. This one
is essentially always true.

### Net effect
With signal 1 dead and signal 3 always on, reaching `>= 2` requires **signal 2** — which needs the
partial current week to already exceed a full-week MRV. That is why the card has never appeared.

## Secondary reasons it stays invisible

- **It renders on one screen only.** `progress_screen.dart:88`. Not the dashboard, not post-workout.
  Even a triggered signal requires the user to open Progress inside the same week.
- **Dismissal is per-week keyed** (`readDeloadDismissedWeek` / `currentWeekKey()`) — that part is
  correct, and not the cause.
- **The provider wiring is correct.** `deloadSignalProvider` watches `completedSetsProvider`, so it
  re-evaluates on new data. Not the cause either.

## J1. `Duration(days: n * 7)` for week arithmetic breaks across DST 🟠
`analytics_repository.loadDeloadData`:
```dart
currentWeek.subtract(Duration(days: offset * 7))
```
and `muscle_progress._rankScore` does the same. Both then use the result as an **exact-equality**
lookup (`weekStarts.indexOf(...)`, `weeks[...]`). A DST transition shifts the value by an hour, the
lookup misses, and **a whole week's volume silently drops out** of both the deload assessment and the
rank score.

`streak.dart` already documents and avoids this exact hazard:
> `// Building via (day - 1) lets Dart normalize month/year boundaries, and avoids the DST hour-drift
> // you'd get from subtracting a Duration.`

The correct pattern is in the codebase; these two call sites don't use it.

## J2. The current partial week is weighted highest in the rank score — rank sags every Monday 🟠
`muscle_progress._rankScore`:
```dart
for (var offset = 0; offset < 8; offset++) {
  final weight = math.pow(0.82, offset).toDouble();   // offset 0 → weight 1.0
  final value  = weeks[currentWeek.subtract(Duration(days: offset * 7))] ?? 0;
  adequacyWeighted   += _volumeAdequacy(value, landmarks) * weight;
  if (value >= landmarks.mev) consistencyWeighted += weight;
```
`offset 0` is the **current, incomplete week** and carries the **largest** weight. On Monday morning
it contributes `_volumeAdequacy(0) == 0` to adequacy and fails the `>= mev` consistency test.

The 8-week decay weights sum to ≈4.44, so losing the offset-0 term costs ~22% of the combined
volume + consistency score — about **11 of 100 rank points, every Monday**, recovering across the
week. That is enough to cross a rank threshold (tiers are 18 points apart), so muscles visibly
rank *down* at the start of each week and back up by the end, with no change in training.

Same root cause as signal 2: a partial week compared against full-week targets. Either prorate the
current week by days elapsed, or start the decay window at the last **completed** week.

## J3. `createDeloadWeek` throws when the deload is most warranted 🟡
```dart
if (rows.isEmpty) throw StateError('Complete at least one workout this week before generating a deload.');
```
It reads only sessions with `started_at >= startOfWeek(today)`. A user who triggered a deload signal
by overreaching last week and then took the early part of this week off — the expected behaviour —
gets an error instead of a template. Basing the deload on the last week **with** training would be
both more useful and more correct.

## Recommendation

Deload is currently a feature that exists in code and cannot occur in practice. Two changes make it
real without loosening it into noise:

1. **Compare completed weeks, not the partial one** (fixes signal 2, and J2 in the rank score).
2. **Replace the dead RPE signal with one that reads data users actually log** — e.g. session volume
   or top-set load falling for 2+ consecutive weeks. Keep RPE as a bonus signal when present, and
   surface an RPE control in the inline row so the data starts existing.

Then bound signal 3 to a recency window (A8) so it stops being permanently on, and re-check whether
`>= 2` is still the right threshold once the signals are real.

# Round 5 — what happens to a user who never fills in RPE

RPE is optional in the UI (a plain text field in the set editor sheet, absent entirely from the
inline row). But three features **gate on it**, and for an RPE-free user all three degrade — one of
them into a hard, silent stall.

## K1. The progression engine permanently stalls at the top of the rep range 🔴

`progression.dart:suggestNextSet`, with `targetRpe` present but per-set `rpe == null`:

```dart
final increaseAllowed = reps != null && reps >= maxReps
    && topSet.rpe != null                       // ← always false for this user
    && topSet.rpe! <= targetRpe + effortAllowance;
if (increaseAllowed && weight != null) { /* add one increment */ }

if ((reps ?? 0) < minReps || (topSet.rpe != null && ...)) { /* hold */ }

return ProgressionSuggestion(
  weightValue: weight,
  reps: ((reps ?? minReps) + 1).clamp(minReps, maxReps),
  rationale: 'Keep the load and add one rep toward the top of the range.',
);
```

Trace a user at the top of an 8–12 range with no logged RPE:
- `increaseAllowed` → false (`topSet.rpe != null` fails) → **weight never increases**
- hold branch → not taken (`reps < minReps` false, rpe null)
- fall-through → `(12 + 1).clamp(8, 12)` = **12** — identical to what they just did

**The app suggests exactly what you already lifted, forever, while the rationale says "add one rep
toward the top of the range."** The value and the sentence contradict each other, and there is no
path out: nothing the user can log without RPE will ever unlock the weight increment.

Two earlier states are also dead ends:
- **No template at all** → `minReps`/`maxReps`/`targetRpe` all null → *"Match last time; add a rep
  range and target RPE to progress."* forever. Combined with F7 (prescription is template-only,
  uneditable in-session) the user is told to add fields they have no way to add from where they are.
- **Template with a rep range but no RPE text** → same message, because the guard is
  `minReps == null || maxReps == null || targetRpe == null`.

## K2. `targetRpe` is parsed by regex out of free-text notes 🟠
`template_repository.dart:186` writes `'RPE ${item.rpe}'` into `prescriptionNotes`;
`active_session_screen.dart:1186 _targetRpe()` reads it back with
`\bRPE\s*([1-9](?:\.\d+)?|10(?:\.0+)?)\b`. A coaching input that gates the whole progression engine
round-trips through a text field. "Keep RPE below 8" parses as a *target* of 8; "RPE 8-9" yields 8.
There is no structured way to set it — only free text or CSV import. It should be a column on
`TemplateExercises` / `SessionExercises`.

## K3. Deload signal 3 is dead for this user (see Round 4) 🔴
No RPE → `rpeAtLoadSeries` empty → the rising-effort signal can never fire, which is one of the two
reasons deload is unreachable.

---

## Recommendation: make RPE enhancing, never gating

Everything the coach needs is **already being logged**. Reps, load, set count, and within-session rep
decay are recorded on every set with zero extra user effort. RPE should modulate the decision when
present, not be a precondition for having one.

### Replace the gate with double progression (standard, RPE-free)

| Observed (already in the data) | Suggestion |
|---|---|
| Hit `maxReps` on **all** target sets | Add one increment, drop back to `minReps` |
| Hit `maxReps` on the top set only | Hold load, push the remaining sets up |
| Between `minReps` and `maxReps` | Hold load, add one rep |
| Below `minReps` | Hold load, own the target first |

This is the classic double-progression scheme and needs no effort input at all. When `rpe` *is*
present, use it exactly as today to gate the increment more conservatively — an enhancement, not a
requirement. The one-line change is dropping `topSet.rpe != null` from `increaseAllowed` and
substituting an all-sets-at-maxReps check.

Also drop `targetRpe == null` from the early-return guard: a rep range alone is enough to progress.
Only `minReps`/`maxReps` should be required, and per F7 those need to be editable in-session so the
no-template path works too.

### RPE-free deload signals

All computable from existing columns:
- **Within-session rep decay widening over weeks** — last set vs first set at the same load. This is
  the closest free proxy for rising effort and it is the natural replacement for signal 3.
- **Top-set load or est-1RM falling for 2+ consecutive weeks** (distinct from A8's "not rising").
- **Session completion rate dropping** — logged working sets vs `targetSets`.
- **Volume down week-over-week while frequency holds.**

### If you want effort data, ask for it in one tap

A numeric 1–10 RPE field requires a keyboard mid-workout, which is why it goes unused. A three-chip
"how did that feel — easy / solid / hard" on the set row maps to ~7 / 8 / 9 and costs one tap. Add it
to the **inline row**, where sets are actually logged, not only the sheet.

But build it after the changes above: nothing should depend on it existing.

## Revised priority

K1 moves near the top. It is silent, permanent, affects the majority of users (RPE is optional and
absent from the fast logging path), and it disables the feature the app is built around — the T2
coaching layer. The fix is small and self-contained in `progression.dart`.

| # | Fix |
|---|---|
| 1 | **G1** — bias normalize to mean 1.0 (+ migration) |
| 2 | **K1** — RPE-free double progression; drop the `targetRpe`/`rpe` gates |
| 3 | **F1 + F2** — `Exercises.isTimed` / distance declaration |
| 4 | Partial-week fix — kills deload signal 2 **and** J2 (Monday rank drop) in one change |
| 5 | **F3 + I3** — exercise edit (name / category / bodyweightFactor) + delete |

# Round 6 — backup/restore, notifications, accessibility, widget, import

Areas untouched by rounds 1–5.

## L. Backup & restore

### L0. What is correct ✅
Worth stating, because it is the most dangerous code in the app and it holds up:
- `PRAGMA foreign_keys = ON` in `beforeOpen` — FKs are genuinely enforced.
- Delete order in `replaceFromPayload` respects FK dependencies (children first).
- All `_rows()` validation and `fromJson` parsing happens **inside** the transaction, so a malformed
  payload rolls the deletes back rather than leaving an empty database.
- `_decodeBackup` sniffs zip magic bytes rather than trusting the extension, and normalises every
  failure to `FormatException`.
- `_csvField` neutralises spreadsheet formula injection (`= + - @`) on user-entered exercise names.

### L1. The backup carries device-local state, and restoring it corrupts both directions 🟠
`appSettings` is exported and restored wholesale. It contains, among preferences:
- `healthExportedSessionIds` — which sessions have already been written to Apple Health
- `muscleAnatomyBackfilled`, `weightEntryBackfilled`, `pullUpExerciseBackfilled`
- `onboardingComplete`

**Restoring onto a new device**: the markers claim every session is already in Apple Health, but
that phone's Health store is empty. Those workouts are then **never exported** and there is no UI to
reset the markers.

**Restoring a pre-v2 backup** (before `appSettings` existed): `_optionalRows` returns `[]`, so the
table ends up empty — clearing the backfill flags. On the next launch `backfillMuscleAnatomyOnce`
re-runs and **overwrites the user's restored anatomy edits on bundled exercises**, defeating the I1
protection through a side door. `onboardingComplete` is cleared too, so the user is dropped back into
onboarding on top of their restored data.

Device-local state should be excluded from the portable payload (or namespaced and skipped on
import). Note this is the 2026-07-26 duplicate-health-record lesson resurfacing from the other side.

### L2. `importFromPicker` can throw outside the "invalid backup" path 🟡
`result?.files.single.path` — `.single` raises `StateError` when the picker returns zero or multiple
files. `_decodeBackup` carefully normalises everything to `FormatException` for the caller's single
error path; this line bypasses it. Use `firstOrNull`.

### L3. Exported zips/CSVs accumulate in the temp directory 🟢
`exportAndShare` and `exportSetHistoryCsv` write timestamped files and never delete them.

## M. Notifications & reminders

### M1. Training reminders die after 28 days of not opening the app 🟠
`buildReminderSchedule` builds a rolling 28-day window of one-shot alerts, refreshed only on app
open, settings change, or workout logged. A user who lapses for a month stops receiving reminders —
**the feature switches itself off exactly when it is the only thing that could bring them back.**

The rolling-window design is otherwise correct (it's what lets one-off rest days and a completed
workout suppress a specific day, which a repeating alarm can't do). It needs a floor: keep one
plain weekly repeating alert beyond the horizon as a backstop, so the chain never fully empties.

### M2. Every notification channel is described as "reminders" 🟢

# Round 6b — persistent lock-screen rest timer (user suggestion)

The right instinct, and it is also the correct fix for **C1** (inexact Android alarm) and **C2**
(no completion state). A posted, self-ticking notification does not depend on an alarm firing at the
right instant — it is already on screen, counting.

## Android — available today, no new dependency
`flutter_local_notifications ^22.1.0` already exposes everything needed on
`AndroidNotificationDetails`:
- `ongoing: true` — sticky, sits in the shade and on the lock screen
- `usesChronometer: true` + `chronometerCountDown: true` — the system ticks it, not Dart
- `when:` set to `endTime.millisecondsSinceEpoch` — the countdown target
- `onlyAlertOnce: true` — no re-buzz on update
- notification **actions** for +15s / Skip

Post it with `showNow` at `start()` rather than `zonedSchedule`, then fire a separate alert at zero.
This removes `AndroidScheduleMode.inexactAllowWhileIdle` from the critical path entirely.

## iOS — needs Live Activities, and the extension already exists
There is no chronometer equivalent; `flutter_local_notifications` cannot do this on iOS. The real
answer is **ActivityKit / Live Activities**, which render on the lock screen and in the Dynamic
Island and tick natively via `Text(timerInterval:)` with no app process running.

Groundwork already present: `ios/LoggedWidget` + `LoggedWidgetExtension.entitlements` exist for the
home widget. Still needed:
- `NSSupportsLiveActivities` in `Runner/Info.plist` — **currently absent** (grepped, no hits)
- an `ActivityAttributes` struct + Live Activity view in the extension
- a method channel from Dart to start/update/end the activity

Interim fallback: `interruptionLevel: .timeSensitive` on the completion notification so it breaks
through Focus modes, plus the full-screen in-app timer.

## Controller change this implies
`RestTimerController._syncBackgroundNotification` currently **cancels** the notification whenever the
app is resumed, and only posts while backgrounded. A persistent timer inverts that: post at `start()`,
keep it for the whole rest period regardless of lifecycle, update on `adjust()`, and cancel only on
`skip()` / `_finish()` / session dispose. That also gives C2 its completion state for free — the
notification flips to "Rest complete" instead of silently vanishing.

Per `lessons.md` ground rule 6: after this lands, `flutter clean && flutter pub get && (cd ios && pod install)`,
and verify on a **real backgrounded device**. A green simulator build proves nothing here.
